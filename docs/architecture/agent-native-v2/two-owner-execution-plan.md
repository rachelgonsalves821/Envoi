# Envoi agent-first onboarding: two-owner execution plan

**Prepared:** 2026-10-08. **Status:** reviewable plan; no implementation PR is merged or deployed by this document.

This plan implements the checked-in [Envoi Agent-Native Architecture Build Plan v3](build-plan-v3.md) in its required order. The release objective is simple: a human asks an independently hosted agent to connect itself to Envoi; the human verifies and authorizes it; the agent keeps one stable Envoi identity, receives durable work, and collaborates without handing runtime secrets to the model or requiring the human to prompt it for every message. Envoi does not host customer agent runtimes. Phase D interoperability is subsequent work, not a dependency for agent-first onboarding.

### A3. Pause semantics — before connector lifecycle

- **First deliverable, Owner A:** Publish a versioned pause/auth/error contract and executable responses in `docs/architecture/agent-native-v2/handoffs.md` and `test/contract-fixtures/` **before** A3 server edits. Cover at least `AGENT_PAUSED`, `CREDENTIAL_REVOKED`, `ACCESS_TOKEN_EXPIRED`, `REFRESH_REPLAY`, `REFRESH_RECOVERY_EXPIRED`, `CASE_CONTROLLED`, `ACCOUNT_CHANGED`, retryable network/5xx and rate-limit behavior. Each code needs status, response example, next allowed operation and A2 lifecycle mapping. Owner B approves client impact before consuming it.
- **Owner A:** Separate `canReceive` from `canAct`; accept and hold work for paused recipients; hold queued outbound work from paused senders; allow authenticated refresh/status while paused; stop claims and writes; preserve SSE; publish explicit pause/resume states and a resume wake event. Agent pause applies across that agent's cases; existing `CASE_CONTROLLED` remains case-scoped and does not pause the whole agent. Either control blocks action, while a case resume cannot override an agent pause.
- **Long-pause rule:** A1's 30-day rolling inactivity expiry **continues while offline**, including during human pause; no immortal bearer token is created. A paused online installation may refresh for status only. If an offline installation expires, resumed work stays held and the owner must authorize a **reconnect to the same identity**, not enroll a replacement agent; automatic refresh or execution with expired credentials is forbidden. The Phase A fixture must prove both an online refresh across pause and an expired offline reconnect path. Reconnection must retain address, cases and history.
- **Held-work rule:** Pause alone never consumes delivery/work attempts, advances backoff, or dead-letters. Keep eligible work durable until resume, explicit human cancellation or a separately documented data-retention action; expose held age and count to oversight. Pausing during a fenced claim invalidates further writes/settlement, allows the lease to expire or be released without an attempt increment, and reoffers it on resume with the same idempotency/fence protections. External effects already committed before pause remain auditable and are not silently retried.
- **Owner B:** Review the frozen response/event contract and add client fixtures for each pause state. Do not yet implement the full state machine or modify server code.
- **Gate:** Server tests cover the v3 pause matrix plus 30+ day offline expiry/reconnect, held attempt counts, in-flight lease, existing case pause interaction and rotation during pause. A valid paused credential must not be misreported as generic 401; an actually expired or revoked credential still fails authorization.

### A2. Connector lifecycle — after A3 contract

- **Owner B:** Implement `STARTING`, `RUNNING`, `DEGRADED`, `PAUSED`, `NEEDS_RECONNECT`, `REVOKED`, `STOPPED` in the existing shared connector, reused by Hermes/OpenClaw/xAI. Use stable server codes rather than HTTP status alone; keep durable state and bounded retry; never silently re-enroll or retry a revoked credential.
- **Owner A:** Preserve the A3-published error/status fixtures and verify server-side revocation and pause enforcement. No second lifecycle engine in `src/**`.
- **Gate:** Client fixtures and local real-service tests cover restart, outage, pause, recovery and revoke.

### A4. Resilient wake — after A2

- **Owner A:** Publish durable work-available/resume events and cursor/delta behavior using the existing stream and queue. Expose next eligible retry time where practical. Keep the queue, not a notification, authoritative.
- **Owner B:** Make SSE the low-latency trigger; resume from cursor, delta-recover gaps, always try a claim after reconnect, and keep a moderate jittered safety poll for retry/lease eligibility. No new WebSocket service or parallel queue.
- **Gate:** Drop SSE and restart the connector; retry-delayed and offline work still processes once without a new event.

### A5. Minimal presence and Phase A hosted acceptance

- **Owner A:** Store conservative `lastSeenAt`, refresh, claim and processed timestamps on the existing credential family; expose them in a bounded status response. Do not introduce `AgentInstallation` yet. Define these fields as an installation-presence projection so Phase B migrates them once, rather than reinterpreting the agent identity as a runtime.
- **Owner B:** Show “seen recently”, “paused”, or “needs reconnect” without equating enrollment or an open browser with a running runtime.
- **Both:** Run the v3 Phase A real-Hermes fixture on a staging release with a verified SHA: inbound work, restart, pause/held work, refresh across pause, lost refresh response, SSE failure and safety poll, delayed retry, then revoke and deny all later actions. Record request IDs, status, exact SHA and owner signoffs. **Phase B cannot become the default until this passes.**

### B. Agent-led onboarding — design in parallel, enable after Phase A

- **Owner A:** Implement pending `AgentRegistration` with no operational rights; a **database-backed** registration rate limit and pending-registration cap that survive Container restart; authenticated human claim with matching verification code, workspace membership and permission intersection; one-time private activation; first-class `AgentInstallation` tied to a persistent `Agent Identity`; installation revoke/reconnect/presence and migration from existing credential families. Specify code entropy/format, lifetime, wrong-guess cap, enumeration-safe errors and abandoned-registration cleanup in the reviewed contract before coding. Reuse one approval/authorization implementation. Preserve old inbox-backed identities, addresses, cases, receipts and history through an explicit migration and reversible rollback. Publish endpoint schemas, migration/rollback fixture and restart test first; in-memory rate limits or live SSE subscribers cannot be the safety boundary.
- **Initial registration contract to review:** eight uniformly random human-readable characters displayed as `XXXX-XXXX` (at least 40 bits of entropy), 10-minute expiry, five wrong claims before invalidation, and deletion of unclaimed records within 24 hours. Claim responses must be indistinguishable for missing, expired and wrong codes. The bootstrap credential is separate from the display code, bound to one registration and never grants send/claim; registration creation is rate-limited durably by source and bounded per pending owner/workspace. Owner A records any changed threshold with its security rationale in the handoff before implementation; Owner B confirms the helper and UI copy.
- **Owner B:** Build and package trusted `envoi-link connect`, private bootstrap/activation/credential storage, capability detection and chosen delivery mode, sanitized status/doctor output, `/connect` page plus `SKILL.md`/`HEARTBEAT.md`, code-matching claim UI and the default “tell your agent” flow. Retain current Quick Connect under Advanced until real acceptance. The model sees only URL/code and safe status, never operational tokens. Do not claim a closed provider is reachable from a skill file alone.
- **Gate:** Fresh real Hermes and OpenClaw installations complete the v3 Phase B sequence without token copy into chat; agents message each other, restart, recover missed work and stop after installation revocation. A second runtime can reconnect the same identity without losing address/cases/history. Backend and UI agree on installation status.

### C. Case-scoped model tools — after Phase B acceptance

- **Owner A:** Create server-bound `CaseSession` after trusted host claim; short-lived tool scope binds agent, installation, work, case, counterparty, fence and expiry. Implement case-snapshot/reply/propose/decide/authority/human-request/assets/complete tools plus a signed, challenged generic HTTPS wake adapter. The adapter must reject redirects and private/link-local/metadata destinations, re-resolve and pin public DNS to resist rebinding, bound connection/read timeouts and response size, and rate-limit retries. Reject stale leases, third-party case IDs and unscanned assets. The model cannot choose a new recipient or case inside a session.
- **Owner B:** Move host claim/renew/settlement and credentials out of model-visible prompts; adapt Hermes/OpenClaw/xAI to snapshot-first, case-scoped tools with a temporary compatibility fallback. Run two simultaneous multi-turn cases, safe file exchange and human decision across both owners.
- **Gate:** One exact hosted commit passes end-to-end cross-owner, restart, revoke, pause, duplicate, file-denial and human-oversight fixtures. “Case completed” requires the canonical outcome receipt, not merely a processed-message receipt.

### D. Later interoperability, not an onboarding prerequisite

After C, Owner A can add relationship/trusted-discovery policy and an A2A adapter over canonical Envoi cases (`AgentCard` → approved identity/gateway, `Task` → Case, `Artifact` → Asset). Owner B can supply A2A client tests and setup guidance. Neither owner creates a second inbox, public arbitrary-address lookup, or separate conversation store. Muse/Instinct provider approval and app-closed wake remain independent provider gates; #21 does not prove them.

## Review and handoff discipline

Every PR names its base SHA, owner, changed paths, API contract revision, client/server compatibility, focused tests, hosted evidence still missing, and rollback target. Owner A provides a small executable fixture in `test/contract-fixtures/` before Owner B implements a dependent client. Owner B reports expected versus observed API results without patching server files. Owner A integrates reviewed heads on the integration branch, reruns all checks there, deploys that **same exact combined commit** to staging after release authorization, and records backend, connector, browser and provider results against its SHA. Preserve the distinction between implemented code, CI, deployment and live acceptance. This plan itself authorizes no application merge, staging promotion or beta deployment.
