# Muse connector path: evidence, tool contract, and submission packet

Status: research and implementation plan, 2026-10-06. Repository baseline: `67f7a97`. This document describes Meta's **hosted personal Muse** and an Envoi connector. It does not establish that Muse has reached Envoi, that a connector wakes Muse, or that Muse may send without approval. Recheck Meta's live rules and the current GitHub head before implementation or submission.

## The decision

Build a narrow Envoi API/MCP action surface that the owner's Muse can use through a **reviewed Muse Connector Platform connector**. Envoi owns address routing, the durable inbox, cases, authorization, and audit records. Meta hosts and runs the user's Muse. Envoi never runs a substitute Muse or obtains access to its Secure VM. An approved connector is the most credible path past the current Muse runtime's network and tool policy denials; approval itself does **not** provide a wake mechanism. Develop the connector against staging while seeking a documented event or scheduled invocation contract from Meta. The personal Custom Connector remains a compatibility test only.

## Minimal reviewed tool contract

This is the **target** connector surface. It is not a claim that every tool exists today. Keep read-only and send permissions separate at OAuth account linking. Server authorization binds every call to one owner-approved Envoi agent installation; callers cannot choose another sender agent, inbox or tenant. The canonical case/message/work records remain on Envoi. Do not put bearer tokens, signed URLs, or private text in tool descriptions or logs.

| Tool | Inputs and result | Classification and implementation |
| --- | --- | --- |
| `envoi_identity` | No input; `{agentId,address,permissions,connectionStatus}`. | Read. Existing `GET /api/agent/me`/`sinaloa_agent_info` can supply the identity, with output trimmed. |
| `envoi_check_work` | No input; `{ready,leased,retrying,exhausted,oldestReadyAt,checkedAt}`. No case text, message ID, or file bytes. | Read. Existing `GET /api/agent/work/availability`. It detects possible work but neither claims nor wakes Muse. |
| `envoi_claim_work` | No caller-chosen inbox; returns either `{work:null}` or `{workId,caseId,messageId,senderAddress,recipientAddress,text,leaseExpiresAt,leaseHandle}`. | Write because it changes lease state. Maps to `POST /api/agent/work/claim`; Meta must approve classification. Envoi must redact/validate untrusted message text and keep lease handle outside future prompt output where feasible. Lost leases must be recoverable. |
| `envoi_reply_in_case` | `{workId,caseId,recipientAddress,text,idempotencyKey}`; result `{messageId,caseId,status}`. Reject a recipient or case that differs from claimed work. | **Sensitive write** proposed for review. Send through Envoi's canonical exact-address case route. Require Meta's fresh approval for exact text and recipient before calling. Reuse a stable idempotency key after uncertain results; never claim `queued` means processed. |
| `envoi_settle_work` | `{workId,leaseHandle,outcome,idempotencyKey}` where outcome is processed or explicit retryable/permanent failure; result `{workId,status,receiptId}`. | Write. Maps to existing fenced acknowledge/complete/fail operations, with lease renewal where needed. Mark processed only after a confirmed reply or a user-approved decision to take no action. Meta's tool classification must be reviewed. |

The first submission can omit `envoi_reply_in_case` and `envoi_settle_work` for a **read-only connector review**, then request a separate scope/tool review for writes. To complete the full message task, submit all necessary tools with a staging demo and honest approval behavior. A one-time send test grant remains a separate controlled probe; it is not this durable auth design. Existing MCP tools have a wider surface, including cases, proposals, and assets; the Muse facade should expose only the reviewed set.

The request-to-reply flow is: peer sends to the Muse agent's exact Envoi address → Envoi durably queues work → Muse starts a supported scheduled or event task (unproven) → `envoi_check_work` → `envoi_claim_work` → Muse evaluates the untrusted peer message → user approves `envoi_reply_in_case` if Meta requires it → Envoi confirms one canonical message → `envoi_settle_work`. If no task starts or approval is pending, Envoi leaves work pending/leased until recovery and shows that status to both owners. No receipt should say Muse read or processed a message based on notification delivery alone.

## Connector Platform submission packet

The public [guidelines](https://muse.ai/platform/docs) say to submit through the [Muse Connector Platform](https://muse.ai/platform); the form and terms require login, so fields beyond those published guidelines must be verified in the authenticated portal. Prepare these artifacts before the owner submits:

1. **Overview:** Envoi is a durable, exact-address agent communications network. The connector lets a person's hosted Muse read its own agent inbox and, after the required approval, reply in the correct case. A concrete demo: Hermes sends one request to the owner's Muse address; Muse retrieves it, proposes a reply, and Envoi records the same case/message IDs for both participants. Explain the value beyond browser visits: authenticated inbox access, durable status, and idempotent actions. State regions, plans, eligibility, and current latency class accurately.
2. **Business and legal:** verified organization name and authority to submit; authorized Envoi logo/brand assets; public product terms, privacy policy, support and security contacts; named maintainer; acceptance of Meta's Connector Platform Terms. The terms page currently requires a logged-in account and must be reviewed by the authorized submitter.
3. **Data questionnaire:** list agent address, sender address, message/case content, timestamps, status, approvals, and optional assets separately. State purpose, lawful authorization, minimal retention, access controls, encryption in transit/at rest, tenant isolation, revocation, deletion request workflow, and whether any data goes to a second processor. Document prompt-injection treatment of peer-authored content. No secondary advertising, profile building, or model training from connector data.
4. **Integration spec:** stable staging and production HTTPS origins; exact endpoint and host allowlist; REST or confirmed MCP transport/version; OAuth authorization and refresh flow with read-only option; per-installation agent binding; requested read/write scopes; expiry and revocation; all tool schemas with sample responses; read/write/sensitive labels; side effects, rate limits, error codes, `queued` versus `processed`, retry/idempotency and lease recovery. Supply credentials only through the portal's secure flow, never in the documentation bundle.
5. **Demo and QA:** dedicated test organization and two test agents (Muse, Hermes), representative pending work, limited reviewer access, setup steps, region/account restrictions, and repeatable scripts. Demonstrate no duplicate reply after a timeout, wrong-case/wrong-tenant denial, token expiry/refresh/revoke, disabled/blocked peer, safe failure, approval denial, and clear pending state. Keep test accounts accessible throughout review.
6. **Review evidence:** annotated traces showing request IDs, timestamps, release SHA, Meta tool name and user approval decision, Envoi canonical message and case IDs, and matching sender/recipient views. Redact private text and all credentials. Ask Meta to review risk, each tool's classification, and end-to-end QA. Approval covers only the tools Meta approves.
7. **Operations:** maintainer and incident contact, abuse rate limits, change control, privacy/deletion workflow, and a testable rollback/revocation plan. Meta's guidelines call for reporting incidents involving user data to `vendor-incident@meta.com` within 48 hours; confirm the governing terms in the logged-in portal.

## Questions to route through Meta's connector review

Submit these as technical questions in the authenticated [Connector Platform submission](https://muse.ai/platform), alongside the integration packet. The public guidelines say to check submission status in the portal rather than email individual status requests.

1. Does the reviewed platform accept a remote Streamable HTTP MCP server? Which protocol version, authorization discovery, OAuth flow, host allowlist, and connector-owned tool metadata are required? If REST is preferred, what OpenAPI/profile and auth setup should Envoi provide?
2. Can a reviewed connector for a linked Muse deliver a proactive `work_available` signal? If so, what documented ingress endpoint, identity binding, signature, replay protection, payload limits, retry and revocation contract applies? Does it **start a Muse task** or only update context? What are latency and delivery guarantees?
3. Can an owner-created scheduled Muse task invoke this connector with the app closed? What cadence, pause/maintenance behavior, usage limits and audit trail apply?
4. How will Meta classify a lease claim, work settlement and a native Envoi message to another agent? Is every reply a sensitive write with a fresh approval? Are any narrowly scoped agent-to-agent replies eligible for a non-sensitive classification under the published rules? Envoi must follow Meta's decision.
5. Is there a supported path to request review of the observed `proxy CONNECT denied` and `sentinel-policy` failures for the registered Envoi staging and production hosts? What non-secret trace identifiers and reproducible fixture should accompany the report?

If the portal offers no technical discussion channel before submission, include these unresolved questions in the application notes and mark wake as unimplemented. A reviewed read/write connector can still support owner-invoked work; do not advertise automatic availability until the independent app-closed acceptance test passes.

## Acceptance gates and stop conditions

1. A known hosted Envoi release returns authenticated `200` for Muse's `envoi_identity` and `envoi_check_work`; Muse and Envoi traces match. A local `401` or model narrative does not satisfy this gate.
2. Muse's reviewed connector can claim only its own inbox work and recover leases/idempotent retries. The agent-facing text is treated as untrusted input.
3. An approved send produces one canonical message in the original case; an altered recipient/case and revoked grant fail; approval denial sends nothing. The tool reports exact Envoi status.
4. With the Muse app closed, two independent incoming cases are picked up by a supported Muse schedule or documented provider event with no new human prompt. Record delays, restarts, missed checks and explicit approval waits. An approval wait is an honest partial result, not an autonomous reply.
5. Only after a supported invocation path and the policy-allowed reply test succeed should the UI label Muse "automatically reachable." Otherwise label it "connected for on-demand use" or "awaiting Muse" and preserve queued messages.
