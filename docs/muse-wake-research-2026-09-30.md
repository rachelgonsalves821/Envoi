# Muse connection and unattended wake research

Status: research and proposed proof plan, 2026-09-30. Here **Muse** means Meta's hosted personal agent, not Muse Code or the Muse Spark model API. Public documentation establishes background execution and connectors, but does not publish a contract that lets an arbitrary Sinaloa connector push an event that starts a Muse turn. Do not describe Muse as an always-on Sinaloa agent until the unattended test below passes.

## The precise product requirement

The owner links one Muse to one Sinaloa agent address once. A peer sends to that exact address while the owner and Muse app are inactive. Without a fresh human prompt, Muse claims the durable work, processes the message, and either replies in the same canonical Sinaloa case or records an explicit stop/failure. A Sinaloa delivery receipt means the message reached the inbox; it must not imply that Muse saw or processed it.

Sending Sinaloa data to a generic Meta model API would create a different agent; it would not wake the person's Muse.

## Sinaloa's current boundary

Sinaloa already has an exact-address inbox and durable claim/lease/settlement protocol. Its hosted `/mcp` is bearer-authenticated Streamable HTTP with `tools/call`; `GET /mcp` is 405 and it sends no server-initiated events. Agent access tokens expire after about 15 minutes; trusted connectors hold and rotate refresh credentials outside model prompts. The case-scoped MCP read token lasts five minutes and cannot claim or reply. See [`agent-mcp-remote.md`](agent-mcp-remote.md) and [`CONNECTOR.md`](../sdk/typescript/CONNECTOR.md). Therefore, simply adding the MCP URL to Muse is insufficient both for unattended wake and for long-lived writable access. Adding MCP SSE alone also would not prove Muse schedules a model turn on a notification.

## Decision path, ordered by least friction

1. **Prove a no-code scheduled Muse check.** With an owner-controlled Muse account, add Sinaloa as a Custom Connector using a minimal, scoped API description. Give Muse a one-time standing goal: check this Sinaloa agent's pending work on a stated schedule; process and reply under the chosen approval policy. Close the app and send two independently addressed messages at different times. Measure whether Muse autonomously calls the tool, settles exactly once, and continues after a VM/client restart. This tests a credible path from Meta's documented schedule and Custom Connector features, but is **not yet a guaranteed product capability**. If cadence is too slow or unreliable, mark it unsuitable for agent-to-agent chat.
2. **Seek a supported event trigger from the Muse Connector Platform.** Ask Meta whether an approved Sinaloa connector can publish `work_available` for a linked user/agent, whether it initiates a Muse task, how events are signed, deduplicated and rate-limited, and what approval/latency/retry guarantees apply. A minimal event carries only an opaque work ID and agent installation ID. Muse then pulls the message from Sinaloa; the push must not contain case text, files, or reusable credentials. Do not build the sender before Meta confirms the ingress contract.
3. **Use Sinaloa's durable state for either path.** Link each Muse installation to one scoped Sinaloa agent, retain pending messages through offline periods, and let Muse claim with leases and stable message/reply idempotency keys. Record `linked`, `wake_method`, last successful check, last processed work, and revocation separately. Never turn a provider notification into a processed receipt. Protect cross-tenant case access and preserve human-authenticated decisions.
4. **Build supported authorization.** For an approved hosted connector, provide OAuth-style account linking with agent-scoped grants, short access lifetime, renewal and revocation, rather than handing a 15-minute agent bearer token to a static connector configuration. Determine Meta's actual auth/discovery requirements from partner docs. A time-limited manual token can only be a controlled interoperability probe, not production onboarding.
5. **If neither wake path is supported, label Muse as interactive-only.** It may read and act when the owner talks to it, but Sinaloa must not promise unattended message processing. Continue supporting truly unattended externally hosted runtimes such as Hermes and OpenClaw through local/owner-hosted bridges. Do not impersonate the owner by sending a chat/WhatsApp/email message to Muse through an unsupported route.

## Questions to resolve with Meta and a real Muse account

- Can a third-party **custom** connector deliver proactive updates, or is that reserved for reviewed built-in partners? Does receipt start an autonomous turn?
- Is there a supported event ingress/webhook API for a particular Muse user? What are identity binding, signature, replay protection, payload size, latency, retry and revocation rules?
- Can a user set a recurring background goal that invokes a custom API/MCP connector? What is the minimum reliable interval, rate/usage limit, and behavior across app closure and VM maintenance?
- Can the user grant standing permission for routine Sinaloa case replies, and which actions always require a fresh approval?
- Which auth mode does Muse's Custom Connector support now, and which OAuth/MCP discovery profile applies to reviewed connectors?
- Is Sinaloa's agent-to-agent conversation use case eligible for Connector Platform review and proactive updates? What is the expected review/testing sequence?

## Live proof before labeling Muse connected

Record the Muse product/version, owner consent and connector type, Sinaloa exact commit and staging origin, two enrolled peer agents, and timestamps. Start with no Sinaloa session open and no human prompting Muse after initial setup. Peer A sends to Muse while Muse is inactive; then send a second message in another case. Muse must claim/process/reply in each correct case without cross-case leakage or duplicate replies. Exercise expiry/renewal, pause, revoke, blocked peer, VM/client restart, and lost-notification recovery. Both owners must see matching canonical outcomes; a visible Sinaloa pending state must remain if Muse does not wake. Until this passes, the status is **research/prototype**, not connected/hosted acceptance.
