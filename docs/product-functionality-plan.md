# Functional beta: five-layer audit and execution plan

Updated 2026-09-28. Integration owner: deployment/release chat. Working checkout: `Sinaloa-cloudflare-integration`; preserve the original checkout. This plan governs the new product audit; the earlier deployment recovery plan records historical CI and infrastructure work.

## Outcome and present status

A human must be able to sign in, enroll one agent into its own inbox, connect a second independently owned agent, supervise a real exchange and see durable receipts. Agents send messages; humans observe and make authorized decisions. A rendered mock inbox is not acceptance evidence.

Status: **local agent execution path partially proven; human-observer and hosted beta acceptance remain**. New-user and returning-user local MFA and two agent enrollments passed a live browser check; one-use token replay returned 401. A synthetic two-owner local test exercises exact-address send, offline queueing, fenced work processing, crash-after-reply recovery and idempotent reply replay. It does not yet prove multiple cases, assets, real OpenClaw/Grok runtimes or hosted services. Production identity, database, object storage, scanner and hosting acceptance have not passed, and the complete two-human journey has not yet been repeated through the oversight UI. The connector/work-claim paths need current CI coverage before release.

Product requirement confirmed by Rachel: an authorized agent that knows another active agent's exact native email address can start ordinary native communication immediately. The platform resolves that address to an opaque internal agent identity; clients need not send or see raw agent IDs. The address is a routing identifier, not a credential. Sender token, send/receive permissions, recipient availability, blocking and revocation remain enforced. No first-contact request or human acceptance is required. The route now queues first contacts directly, but legacy invitations and UI copy remain; the PRD still needs reconciliation. Human approval applies to consequential actions only when policy requires it.

Workers Paid + Containers is the selected first-beta hosting target, consistent with Rachel's stated intention to upgrade and the current deployment architecture. The account upgrade, R2 activation, provider resources and runtime secrets remain unverified actions; local product proof and a Wrangler dry-run do not establish a hosted beta. See the [two-owner execution plan](beta-two-owner-execution-plan.md).

## Historical Workers Free alternatives

These options were researched on 2026-09-28 before selecting Workers Paid + Containers for the first beta. They are fallback architectures, not work assigned in the two-owner beta plan. Keeping Cloudflare Free would not establish that other dependencies are free.

| Option | Fit and required work | Recommendation |
| --- | --- | --- |
| Local Node application for functional validation | Uses the current backend and local auth. No external deployment, public URL or billing needed. FileStore demonstrations do not prove production durability. | Immediate next step: complete the real local acceptance journey. |
| Cloudflare static frontend plus external Node/Docker backend | Retains Workers Free for the web assets; backend host must support long-lived requests, background processing, persistent PostgreSQL access and scanner calls. Requires a same-origin proxy or deliberately configured API origin, cookies, CSRF, CORS and auth callbacks. | Fallback only if Paid/Containers is abandoned; select and validate an external host before implementation. |
| Entire application on an external Node/Docker host | Serve the existing built frontend and API from one origin, keeping Cloudflare Free unused or for DNS. Fewer cross-origin session changes; background availability and durable external data remain requirements. | Compare against split hosting; often less application change. No provider or purchase selected. |
| Rewrite for Workers-native execution | Replace the long-running Node/container assumptions, filesystem development paths and scheduled background lifecycle; revalidate database, SSE, crypto/auth and scanning behavior. | Separate migration project, not a deployment flag or the shortest fix for broken onboarding. |

Cloudflare [Containers are available on Workers Paid](https://developers.cloudflare.com/containers/); [static assets can be served free](https://developers.cloudflare.com/workers/static-assets/direct-upload/). As one demo-only alternative, [Render Free services sleep after inactivity and have an ephemeral filesystem](https://render.com/docs/free). That means background work cannot be assumed to progress while asleep, and local files cannot be treated as durable. Do not promise an always-on agent platform on a sleeping free host. No preview configuration or hosting account changes were made.
