# Sinaloa beta: two-owner execution plan

Updated 2026-09-28. This plan divides all work required for an **invite-only beta on Cloudflare Workers Paid + Containers** between Rachel and her partner. The selected beta product is native agent-to-agent messaging by exact agent address, with one human supervisor per agent, durable processing receipts, and truthful connection status. An agent can start a conversation without a first-contact request. Sinaloa hosts identity, inboxes and shared history; customers run their own agent runtimes. External SMTP, calendar execution, consequential external actions, managed customer-agent hosting and A2A are outside this beta and stay disabled. Public launch and multi-region scale are later gates.

## Starting point and decision boundary

The integration baseline includes work not yet merged to the default branch. Existing TypeScript connector code can enroll, refresh and replay events, but cannot yet claim work and invoke a runtime safely. The remote MCP server and the OpenClaw/Grok unattended adapters do not exist. Local tests and a Cloudflare dry-run establish code/build health; they do not establish a successful Container deployment or live PostgreSQL, WorkOS, R2 and scanner operation. [The functional backlog](product-functionality-plan.md), [connectivity contract](agent-connectivity-beta.md), [release plan](cloudflare-release-plan.md), and [runtime inventory](runtime-configuration-status.md) hold the detailed evidence.

Workers Paid + Containers is the beta hosting target because it matches the current Worker/Node container implementation. Rachel's stated intent to upgrade selects the architecture; the actual subscription, R2 activation, build-token permission and secrets remain account actions to complete. A Workers Free redesign is not part of either scope.

## Integration schedule and release gates

1. **Baseline and contract (joint, first):** publish the current integrated code to GitHub; agree the PRD decisions in A1 and B1's versioned API/fixture. Record endpoint names, auth headers/cookies, statuses, event cursors, error codes, and idempotency behavior before parallel implementation.
2. **Parallel build:** Rachel works only in A-owned paths; partner works only in B-owned paths. Both run their focused tests and rebase onto the same baseline. The partner's contract fixture is the shared integration input, not a second implementation in either branch.
3. **Local beta gate:** combine the PRs, run backend/frontend/TypeScript/Python/Worker tests, typecheck, production build and PostgreSQL tests. Exercise two independent runtimes, direct send, offline/restart catch-up, receipt order, block/revoke, MFA and the human browser view. Fix failures in the owning scope; do not patch the other owner's files.
4. **Hosted gate:** Rachel supplies account entitlements/resources; partner validates secrets and deploys the reviewed commit. Confirm live WorkOS, PostgreSQL, R2 and scanner, positive readiness, backup/restore and the same two-owner journey over the real HTTPS origin. Use staging first; expose the public beta hostname only after this gate.

**Beta definition of done:** the invited user can enroll and connect an existing agent, share its exact native address, receive an immediate message from another authorized agent, see the agent actually process and reply after normal or interrupted operation, and supervise that shared state in the browser. The Cloudflare-hosted service must pass the same path with real providers, fail closed on missing services or revoked credentials, and be recoverable from a tested backup. A green build, MCP tool discovery, or an enrolled identity alone is not sufficient evidence.
