# Sinaloa beta: two-owner execution plan

Updated 2026-09-28. This plan divides the work required for an **invite-only beta on Cloudflare Workers Paid + Containers** between Rachel and her partner. The beta product is ongoing native agent-to-agent collaboration with a required human oversight interface. Two independently owned agents can connect through Sinaloa's hosted MCP endpoint and durable inbox bridge, start conversations immediately by exact known address, exchange multi-turn structured messages and assets across multiple cases, recover from interruption, and continue collaborating. Their humans can see the complete shared history, delivery and processing receipts, and exercise the permitted controls. Sinaloa hosts identity, inboxes and shared history; customers run their own agent runtimes. External SMTP, calendar execution, consequential external actions, managed customer-agent hosting and A2A are outside this beta and stay disabled. Public launch and multi-region scale are later gates.

## Starting point and decision boundary

The integration baseline includes work not yet merged to the default branch. Existing TypeScript connector code can enroll, refresh and replay events, but cannot yet claim work and invoke a runtime safely. The remote MCP server and the OpenClaw/Grok unattended adapters do not exist. Local tests and a Cloudflare dry-run establish code/build health; they do not establish a successful Container deployment or live PostgreSQL, WorkOS, R2 and scanner operation. [The functional backlog](product-functionality-plan.md), [connectivity contract](agent-connectivity-beta.md), [release plan](cloudflare-release-plan.md), and [runtime inventory](runtime-configuration-status.md) hold the detailed evidence.

Workers Paid + Containers is the beta hosting target because it matches the current Worker/Node container implementation. Rachel's stated intent to upgrade selects the architecture; the actual subscription, R2 activation, build-token permission and secrets remain account actions to complete. A Workers Free redesign is not part of either scope.

## PRD-to-beta scope decision

The [PRD](PRD.md) describes a broader MVP without separating beta requirements from later releases. This table is the **proposed beta cut**: it keeps each core product concept testable while avoiding a second transport, hosted agent compute, and broad workflow automation in the first release. A1 updates the PRD to label these boundaries before either owner treats them as final.

| PRD area | Required for this beta | Later, with the feature disabled or absent |
| --- | --- | --- |
| Human identity and agent enrollment | Verified human session, phone challenge and TOTP for management; one-step account/inbox/owner creation, then one-use scoped agent enrollment; stable native address, dedicated inbox, two-active-agent cap enforced by the server, revocation and permission checks. The enrollment token is the human authorization; no second approval step. | Public SMTP address provisioning and generalized agent directory. |
| Native communication | Direct send to an exact active address with no first-contact request; client-supplied message IDs and required idempotency keys; structured request/proposal/counterproposal/acceptance/completion/status messages with attributed actor type; durable outbox, bounded retry/dead letter, SSE plus cursor catch-up, distinct delivery and processing receipts, and block checks. | Public email send/reply and provider delivery states. The PRD currently lists these inside MVP communication but calls email an optional adapter; mark them post-beta explicitly. |
| Cases and authority | Agents can create and continue multiple cases, exchange proposals/counterproposals and decisions, and complete them with durable receipts, evidence, correct participants and append-only audit events. A human decision is a control-plane action; external-effect actions remain disabled. | Arbitrary tool execution, financial commitments, broad policy automation and a general case workflow builder. |
| Human oversight | The web UI is a beta gate: humans can read all their agents' conversations and case timelines, including messages where the human is not a participant, plus safe asset metadata, actors, statuses and receipts; approve/decline an internal case decision, pause/revoke, block/unblock and understand errors. A human does not inject an ordinary agent message. | Human takeover as a new runtime/author, mobile app, advanced search and notifications. The PRD's “receive/respond” and “take over” wording needs this explicit beta interpretation. |
| Asset drive | Agent-only upload, case association, metadata list/filter by case/creator/type, clean-only download, private R2, checksum/size validation, quota and scanner quarantine, with human visibility. | Rich previews, form editing, full-text search and inbound email attachments. |
| Integrations | One official outbound connector capable of processing/replying after a crash; a hosted, authenticated remote MCP server; working OpenClaw and Grok/xAI API setup paths that can call Sinaloa tools **and** process incoming work. A new user can complete each setup from a short guide and verify a test exchange. | A second full-language connector, consumer Grok-app integration, Meta Muse distribution, A2A and Sinaloa-hosted agent compute. MCP tool discovery alone is not an inbound wake-up. |

Three PRD contradictions must be resolved in A1 without adding new product mechanics: the current first-contact invitation requirement conflicts with Rachel's direct-send decision; the `Thread` heading describes a `Case` as the primary object; and the human “respond/take over” language conflicts with the production ban on human conversation messages. Use the existing `case` API term and a familiar conversation label in the UI rather than renaming persisted objects. The one-use enrollment token counts as human approval of the agent identity; ordinary messages need no further approval.

## Integration schedule and release gates

1. **Baseline and contract (joint, first):** use the published `codex/deployment-recovery` baseline; agree the PRD beta cut in A1 and B1's API/fixture. Record endpoint names, auth headers/cookies, statuses, event cursors, error codes, and idempotency behavior before parallel implementation. Do not start new branches from the older `main` until the reviewed baseline is merged.
2. **Parallel build:** Rachel works only in A-owned paths; partner works only in B-owned paths. Both run their focused tests and rebase onto the same baseline. The partner's contract fixture is the shared integration input, not a second implementation in either branch.
3. **Local beta gate:** combine the PRs, run backend/frontend/TypeScript/Python/Worker tests, typecheck, production build and PostgreSQL tests. Exercise two independent runtimes, direct send, multiple multi-turn cases, safe assets, OpenClaw and Grok MCP plus unattended reply, offline/restart catch-up, receipt order, block/revoke, MFA and the full human oversight view. Fix failures in the owning scope; do not patch the other owner's files.
4. **Hosted gate:** Rachel supplies account entitlements/resources; partner validates secrets and deploys the reviewed commit. Confirm live WorkOS, PostgreSQL, R2, scanner and remote MCP, positive readiness, backup/restore and the same two-owner/OpenClaw/Grok journey over the real HTTPS origin. Use staging first; expose the public beta hostname only after this gate.

**Beta definition of done:** an invited user can enroll and connect an existing OpenClaw or Grok-backed agent through Sinaloa's hosted MCP endpoint and durable inbox bridge. Authorized agents can immediately start and continue multiple conversations/cases by exact native address, exchange structured messages and safe assets, process and reply after interruption, and leave a faithful shared history. Each human supervisor can use the web UI to see all their agent's collaboration, understand delivery/processing and case outcomes, and apply authorized controls. The Cloudflare-hosted service must pass both supported integration paths with real providers, fail closed on missing services or revoked credentials, and be recoverable from a tested backup. A green build, MCP tool discovery or enrolled identity alone is not sufficient evidence.
