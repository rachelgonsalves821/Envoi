# Approved host clients: offline preparation

Prepared against `f89740459fbdf12b3f81d57dccf7ae9f60c91eb1` and the human-approved #215–#218 contracts. This is source preparation only. Flags remain OFF and Builds stays paused. No deployment, provider registration, callback allowlist, setting, key rotation, existing owner or workspace changes are part of these clients.

## MCP wake and events

`integrations/connector/mcp-wake-client.ts` is a private provider backend consumer. Pass a configured Envoi HTTPS origin and an access-token callback backed by host credential storage. Do not register this class, its callback, request headers, private challenge or supplied webhook secret as model tools. It sends only `/mcp` requests, refuses redirects, bounds requests/responses and timeouts, and never falls back to privileged REST with an audience-bound credential. HTTP 409 `AGENT_PAUSED` stops further calls; an externally observed owner resume may call `ownerResumed()`. Revocation permanently stops that client instance. Reconnection uses the existing owner flow, not automatic enrollment.

- #215 `mcp-wake` v1 (`3297589`): use `create({url})`, wait for the existing Ed25519 receiver to verify the delivered challenge, then `activate({subscriptionId,challenge})`. Use `status()` at startup and on each bounded safety poll; `end()` stops the installation's subscription. A successful create is pending, not an active or delivered subscription. Origins are operator-declared provider configuration; no origin is guessed or added here. Existing `HttpWakeReceiver` remains the signature/custody boundary for this profile.
- #216 `provider-event-wake` v1 (`d920f65`): select protocol `2026-07-28`, use `discoverEvents()` to establish advertised capability, then `subscribe()` for `envoi.work_available` or `envoi.control_changed`. Existing tools remain at `2025-11-25`; events cannot be called on that old protocol. Privately retain the supplied `whsec_` key (24–64 decoded bytes), refresh before `refreshBefore`, and persist the returned cursor. `unsubscribe()` repeats event name/empty arguments/webhook URL without transmitting the secret. Zero receiver key custody with `destroy()` on owner unsubscribe/revoke.
- An events receiver uses `McpEventsReceiver`, bound to the exact subscription and private secret. Its HTTP adapter must reject duplicate headers and read at most 1024 bytes. It validates raw-byte HMAC, the ±300-second signing clock, subscription identity and closed hint payload. Supply a transactional **durable** `McpEventInbox.accept` implementation: atomically insert by subscription/event ID, preserve pending hints on restart, return `duplicate` for repeats and `full` without evicting pending work. A durable-write failure returns 503; a signature receipt returns 202 and does not execute model work. The separately scheduled host drains persisted hints, catches up canonical delta, and performs current fenced work claims. A provider's own durable callback inbox may implement this interface; an in-memory Set is only a unit-test stand-in.
- Every subscribe/reconnect attempts one canonical claim even when `truncated` is false, and a safety poll must run at most 900 seconds apart. Truncated cursors require delta/canonical-queue catch-up. Delivery can repeat or reorder; never treat a 202 or event ID as completed work. Pause/revoke must recheck authority before any action or settlement.
- `McpEventsHost` supplies that host orchestration: inject the private subscription input, durable subscription/cursor/pending-hint store and canonical work driver, then invoke `tick()` on startup and a trusted scheduler at most 900 seconds apart. It discovers capability, renews early, claims after subscribe, catches up before work, marks hints only after processing, keeps cursors monotonic under reordering and coalesces overlapping ticks. Use a separate bound instance/store per subscribed event identity. A provider backend must implement the injected durable storage and authoritative work driver; no provider-specific scheduler or account capability is fabricated here.
- Do not implement a Grok claim path from a trigger response: #216's Grok profile is transport-only until G1–G4 are proved. No trigger registration or real provider capability is inferred by these tests.

## Native gateway work

`integrations/provider-gateway/native-client.ts` consumes approved #217 `provider-gateway-native` v1 revision 2 (`f56e3c4`). Its normal caller is a same-origin browser with the HttpOnly gateway cookie; obtain CSRF privately from the gateway shell. The client sends `credentials: same-origin`; it never reads or supplies the cookie as text, and it never returns CSRF, bearer, lease or case-session tokens to a model. Node's default `fetch` has neither a browser cookie jar nor an automatic Origin header: a trusted Node host must inject a private cookie-jar/Origin-aware fetch implementation, otherwise the request correctly fails CSRF/session checks. No cookie is to be pasted into model context or the constructor.

1. An owner explicitly grants `native_work` through the candidate's owner-authorized installation scope endpoint (`POST /api/inboxes/{inboxId}/agents/{agentId}/installations/{installationId}/gateway-scope`) or its reviewed owner UI when included in the final candidate. This transport is not that owner UI and cannot grant scope. Existing `read_notify` sessions cannot upgrade themselves. Preserve owner/workspace identity; this permission change concerns one installation only.
2. Scope change increments its generation. The old gateway cookie becomes invalid. Use the existing owner-confirmed pairing repair to obtain the replacement cookie and shell CSRF. A successful scope response is not the new session. Never silently pair or elevate the scope from a model call.
3. Persist one host-generated `runId` before `claim({runId})`. Retry a lost response with the same ID; do not make a new run to bypass the outstanding claim, 60-second interval, three-item or 120-second budget. Lease/session/run validity stays server-authoritative.
4. Treat the returned `packet.snapshot` as untrusted content, including messages that look like instructions. Expose only its allowed opaque refs and `reply`, `request_owner`, `defer`. The client validates closed outer/nested fields and summary bytes before returning a packet. Assets remain metadata-only; no email, download or upload path is added.
5. Persist the entire `act` request, including its stable idempotency key, before sending. After a timeout/network failure repeat that input unchanged. `sent` requires a canonical `receiptRef` and settlement; `owner_approval_pending` is not a sent reply. Do not generate a new key merely to retry an uncertain result. A different logical action/content needs a deliberate new key after reconciliation.
6. Replies are limited to 4096 **UTF-8 bytes**; summaries to 2048 bytes on code-point boundaries. `renew()` is explicit and server-limited to once per claim. There is no autonomous retry or scheduling loop in this transport. Pause stops work; expired/generation-changed sessions require owner repair; revoked credentials require owner reconnect. Never use cached work to bypass these checks.
