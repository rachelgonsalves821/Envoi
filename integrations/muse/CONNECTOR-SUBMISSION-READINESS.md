## What Meta publishes, and what this account showed

- Meta's [Connector guidelines](https://platform.muse.ai/docs) require a submission covering product and business identity, terms and privacy, data processing, endpoint and authentication setup, requested scopes, tool documentation, test-account credentials, and an end-to-end demo. Meta reviews each tool's read/write and sensitive classification and tests permissions and workflows. Approval of one tool does not approve later tools. The [Connector Platform](https://platform.muse.ai/) describes review before directory discovery. These are vendor requirements, not evidence that Envoi has submitted or passed review.
- Under those guidelines a **read** retrieves without changing state; a **write** changes state or acts for the user; a **sensitive write** includes consequential sends. Meta requires approval on **every use** of a sensitive write. A connector cannot quietly reclassify a send as a read, cache a one-time approval for different content, or bypass Muse's prompt. The exact classification of proposed Envoi tools is Meta's review decision.
- No supported Envoi arrival event, recurring reviewed-connector invocation, private auth renewal, or closed-app reply has been observed for this account.
- The sanitized [account observation in PR #179](https://github.com/rachelgonsalves821/Envoi/pull/179) records that Rachel's signed-in Muse web account exposed Settings → Connectors, a Connected tab, a per-connector Background sync control set to Allow, and Goals. No Envoi connector, credential, goal, schedule, or permission was created or changed in that observation. Those controls do not prove that an Envoi connector may use background sync or that a write may proceed without its required prompt. An earlier `custom.envoi-staging` read probe reported Cloudflare `1010` and then Muse `sentinel-policy` egress denial, without an Envoi-origin response; that excluded Custom Connector experiment is not a test of the selected reviewed route.

## Proposed minimum tool boundary for review

This is a **candidate submission inventory**, not an implemented Muse adapter or published wire contract. It uses the existing Envoi authority boundaries: [agent-registration v1](../../docs/architecture/agent-native-v2/handoffs.md#agent-registration-v1) owns registration/installation and permissions; [agent-remote-auth v1](../../docs/architecture/agent-native-v2/handoffs.md#agent-remote-auth-v1) describes `provider_connector` OAuth and `/mcp` access; [case-session and case-tools v1](../../docs/architecture/agent-native-v2/handoffs.md#case-session-v1) govern trusted work claims, scoped actions, idempotency and settlement. The integrated [provider-browser-poll Stage 1](../provider-gateway/IMPLEMENTATION.md) is read/notify only and cannot supply the missing write path. PR [#179's Stage 2 request](https://github.com/rachelgonsalves821/Envoi/pull/179) remains a request, not an approved extension.

| Candidate operation | Envoi permission and effect | Proposed Meta review class | Gate before it can be submitted as working |
| --- | --- | --- | --- |
| Identify the authorized installation and show bounded work availability | `receive_agent_messages`; identity/status is read, and notification is not a claim | Read, **only if** it has no state-changing acknowledgement | Published, deployed endpoint and privately authorized Muse invocation; document exact fields and limits. |
| Read one already authorized case snapshot or inbox item | `receive_agent_messages`; no mutation, no unrelated case or tenant | Read | Prove Muse's grant can reach the exact scoped read and that no credential/internal authority leaks in results. |
| Claim work, renew a lease, release it or settle it | Trusted host operation with lease/fence and current-policy checks; changes work state | Write, **not** disguised as inbox read | A separately approved provider host-action contract and server mapping are required. A provider model must not receive a general agent bearer or case-session token. |
| Reply to the current case | `send_agent_messages`; one canonical message with exact recipient/case and idempotency, after current lease and consent checks | **Propose sensitive write** because it sends a message; Meta makes the final classification | Approved claim/action mapping, exact recipient/content shown in the provider prompt, Meta's per-use approval honored, and a canonical Envoi receipt. If approval must occur for every use, do not promise unattended replies. |

Do not include arbitrary recipient send, asset upload, case completion, owner administration, or a generic HTTP proxy in the first submission. Adding any later tool needs a new Envoi contract and Meta review for that tool. A successful OAuth connection or read is not authority to send. A reply's `202`/queued receipt is distinct from work settlement and from the other agent's receipt.
