## Dots: bounded account and staging sequence

1. Read the actual plugin management page with the owner. Record whether Dots and custom plugin installation are enabled for that Work account. Record the client metadata document URL and exact redirect URI shown by the plugin UI; [ChatGPT's OAuth instructions](https://developers.openai.com/plugins/build/auth) allow client metadata documents and identify a stable or callback-specific `client_id` depending on issuer support. Do not assume that dynamic client registration is required. Compare those observed values with Envoi's published remote-auth contract's client document, exact redirect, PKCE S256, `resource`, scopes and audience rules. A mismatch is `MISMATCH`, not a guessed exception.
2. After Je's full remote-auth server, consent, token, revocation and `/mcp` enforcement are integrated and deployed on a gated SHA, install in a disposable account. Capture redacted OAuth discovery, consent/claim, authenticated `tools/list`, identity/inbox response IDs, one canonical send/reply receipt, refresh, pause and revoke. The current server slice does not supply this full path.
3. For unattended work, inspect whether the exact dot accepts the [MCP Events](https://developers.openai.com/plugins/build/mcp-events) flow: MCP 2.0 `2026-07-28`, `server/discover` event capability, `events/list`, `events/subscribe`, `events/unsubscribe`, user-directed subscription and a signed webhook callback. ChatGPT's documented integration uses webhook delivery; polling and streaming event delivery are unsupported. Envoi needs an approved server contract and implementation before this step can pass. Its normal remote MCP tool surface does not create a subscription.
4. With that contract live, subscribe the dot, close the chat/app, send two distinct native case arrivals, and correlate each signed event ID and subscription ID with a later authenticated claim, typed reply and one canonical settlement. Then lose one event, restart the dot/server as applicable, refresh the subscription, and prove durable catch-up from Envoi's queue. End the subscription and revoke the installation; verify no later action. Capture whether the dot required a human approval for the send. A received webhook response alone is insufficient.

## Grok: bounded account and staging sequence

1. For **consumer Grok**, inspect [Custom connectors](https://docs.x.ai/grok/connectors) and any Business/Enterprise admin provisioning. Record the exact account/plan, public MCP URL requirement, auth options offered by its UI, redirect/client metadata behavior if OAuth is offered, and whether Envoi's `/mcp` can actually be added. The [tunneling guide](https://docs.x.ai/grok/connectors/custom-mcp-tunneling) says localhost/private addresses are rejected. Use the gated hosted Envoi origin, not an ephemeral tunnel, for acceptance. Complete identity/inbox and a real canonical send/reply, then refresh/pause/revoke on the exact product.
2. For **Grok automation**, first prove the account has a webhook-triggered automation and that the running automation can call the **same authorized Envoi connector**. Its incoming webhook uses Standard Webhooks HMAC-SHA256, a receiver secret and `webhook-id`/`webhook-timestamp`/`webhook-signature` headers. Envoi's `http-wake` v1 uses Ed25519 and a receiver challenge under a different contract; the existing sender cannot simply point at Grok's webhook URL. Require a reviewed Lane A adapter or a trusted receiver that verifies Envoi's `http-wake` callback and separately signs the Grok trigger. Do not put work content, agent IDs, access tokens or signing secrets in the trigger body. Verify two closed-app arrivals through authenticated Envoi claim and canonical reply; then duplicate, outage, retry, restart, pause and revoke. A Grok `202` proves only trigger receipt.
3. For **Grok Bot**, inspect whether the account exposes an event-triggered routine whose event source can be Envoi, whether its Bot can use the same Envoi authorization, and whether each send needs approval. Test a narrow event rule with two arrivals while the owner laptop/app is closed. A scheduled poll is a separate mode and needs its own exact cadence, no-work, missed-run and catch-up evidence. A routine existing in UI does not prove Envoi integration.
4. For the **xAI API bridge**, use [`integrations/grok/README.md`](../../grok/README.md) and `mcp-smoke.mjs` for a real xAI-to-hosted-Envoi MCP call, correlate provider completion to a hosted `/mcp` log, and run two distinct cases, restart during queued work, token rotation and revocation. This supplies a separate host row. Offline Vitest simulation and a request containing `type: "mcp"` are not provider execution evidence.

## REQUEST lane-a: exact contracts needed before wake claims

- **Dots:** publish a separate MCP Events contract for authorized event discovery, subscription create/refresh/end, installation binding, least-privilege filters, callback validation and ownership proof, encrypted signing-secret retention/rotation, durable event IDs and cursor/replay, outbound signature, bounded retry, pause/revoke and flag rollback. It must specify a content-free or opaque event followed by authenticated Envoi fetch, and its relationship to the existing queue. Consume OpenAI's documented `events/*` methods and Standard Webhooks profile; do not silently treat Envoi `http-wake` as MCP Events. Add fixtures for invalid callback, wrong principal/filter, duplicate, lost event, expired/revoked subscription, key rotation and rollback. This is a proposal, not an approved wire contract.
- **OAuth wake gap:** the approved remote-auth contract's audience-bound OAuth access token cannot call the REST `http-wake` subscription route, and no approved MCP tool creates that subscription. Resolve this in a separately published contract; do not create a REST audience exception in Lane B.
- **Grok webhook:** determine whether the account's webhook-triggered automation can use Envoi's approved MCP grant. If so, specify an approved sender or trusted bridge from Envoi's durable queue to Grok's Standard Webhooks format, including destination validation, secret custody, rotation, opaque payload, acknowledgement versus actual completion, retries, duplicate IDs, pause/revoke and rollback. The existing `http-wake` v1 Ed25519 notification is not Grok's HMAC request. Reuse the canonical queue and avoid a second independent work ledger. No implementation before contract approval and real account capability proof.

These requests do not change Je's in-flight remote-auth branches or their reviews. Hosted acceptance requires the owner-approved run, exact release and redacted per-host evidence in the Phase B worksheet.
